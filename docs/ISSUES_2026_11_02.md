# 问题总结：VGGT-Ω → Mesh → UV 管线（截至 2026-11-02）

本文记录本轮实现中**实际遇到并已定位**的问题，区分「已修复且有验证」与「仍未解决」。
所有数字来自仓库内的 `*_report.json` / `manifest.json`，不是估计值。

当前管线：

```
RGB → VGGT-Ω → 深度一致性过滤 → TSDF → mesh.ply → ExMesh → OBJ/MTL/PNG + GLB
```

---

## 一、已修复的问题（有数据验证）

### 1. 内参换算错误 —— 焦距差 10 倍

**现象**：导出的 `K_original` 与 ETH3D 官方真值差一个数量级。

**根因**：原实现用 `K_original = A⁻¹ · K_model · A`。`A` 是**相似变换**，这个共轭形式在代数上
会原样返回 `K_model`，焦距与主点都不变：

```
K_model    f = 341.76   (model 宽 624)
K_original f = 341.76   (原图宽 6211)   ← 应为 3410.3
```

因为深度和相机**一起错**，单视图内看是自洽的，只有对着真值才暴露。

**修复**：按像素网格缩放内参。设 `u_model = s·u_original + t`：

```python
f_original = f_model / s
c_original = (c_model - t) / s
```

**验证**（ETH3D kicker，官方 PINHOLE 真值 `f=3410.34`）：

| | 修复前 | 修复后 | 真值 |
|---|---:|---:|---:|
| `K_original.fx` | 341.8 | **3401.7** | 3410.34 |
| 相对误差 | −90% | **−0.25%** | — |

→ `tests/test_coordinates.py::TestIntrinsicConversion`

### 2. 像素仿射（original→model）推导错误 —— 错了两次

**第一次**：用坐标编码探针图反推变换，但探针的目标尺寸取决于 `load_and_preprocess_images`
的 **token 预算**（`_balanced_target_shape`），与传入的 `image_resolution` 不同。传 624 实际得到
768×512，拟合斜率 3.10（应为 2.52）。

**第二次**：缩略图坐标恢复时重复缩放，得到 77.56（应为 0.1005）。

**修复**：不再"测量"，直接调用 loader 自己的
`_crop_to_supported_aspect_ratio` + `_balanced_target_shape` 解析计算，并加断言：

```python
if abs(sx * original_w - model_w) > 0.05 * model_w:
    raise RuntimeError(...)
```

**验证**：`sx·W = 624.00`（模型宽 624），残差归零。

### 3. 一致性滤波用了错误的像素网格

**现象**：内参一修好，多视图一致率立刻从 0.82 掉到 **0.000**（只剩 2 对）。

**根因**：深度图存的是**模型分辨率**，但滤波用 `K_original`（原图像素）反投影。此前
因问题 1 使两者数值相同，错误被掩盖。

**修复**：统一改用 `K_model`。

**验证**：一致率恢复到 0.819。

### 4. TSDF 未观测体素被当成"外部" —— 网格碎成格子

**现象**：网格呈"帘幕/格子"状，非流形边 **50,994**。

**根因**：`sdf = clamp((observed − z)/trunc, −1, +1)` 对表面**之前**的整个空间都返回 `+1`，
于是"自由空间"和"从未观测"无法区分；未观测区被填 `+1` 后，表面被切成一格格孤立面片。

**修复**：
- 只更新 ±trunc 带内的体素；
- 未观测区保留 `NaN`（未知 ≠ 外部）；
- marching cubes 后剔除全部落在未观测区的三角面。

**验证**：非流形边 50,994 → **0**（kicker）。

### 5. Open3D `ScalableTSDFVolume` 返回空网格

**现象**：即使对合成等深度平面，`integrate()` + `extract_triangle_mesh()` 也返回 **0 个三角形**。
`extract_point_cloud()` 同样为空，而 `VoxelBlockGrid` 需要显式 block 分配。

**修复**：改为 `scripts/tsdf_mesh.py` 中的自实现（numpy + `skimage.measure.marching_cubes`），
公式严格按 `MESH_UV_PIPELINE.md` §3.2。

### 6. GLB / MTL 材质导致"纹理全黑"

**现象**：Blender 打开后网格是黑的 / UV 区全黑。

**根因**（三个独立原因叠加）：

| 问题 | 默认值 | 后果 |
|---|---|---|
| GLB `baseColorFactor` | `[0.4, 0.4, 0.4, 1]` | 乘在贴图上，整体压暗 60% |
| GLB `doubleSided` | `false` | 背面（单视图扫描必然存在）全黑 |
| MTL `Ka` / `illum` | `0 0 0` / `2` | 反射率被清零，且响应光照 |

**修复**：统一由 `scripts/glb_writer.py` 写出，并在导出后回读校验：

```
{'attributes': ['POSITION', 'TEXCOORD_0'], 'has_texture': True,
 'baseColorFactor': [1.0, 1.0, 1.0, 1.0], 'double_sided': True, 'images': 1}
```

**另一个前置问题**：trimesh 只在 `len(uv) == len(vertices)` 时才写 `TEXCOORD_0`，而 xatlas 的
UV 按角点索引 → GLB 曾完全没有 UV。现已展开为逐角点顶点。

### 7. 宿主机 PyTorch 进程崩溃（access violation）

**现象**：命令行打印 `[plan]` 后**静默退出，rc=0**，无异常、无 traceback。

**根因**：`torch 2.13.0+cu132` 在**已持有 4.6 GiB 模型**时再 `torch.load` 4.6 GiB 权重，
峰值内存接近 9 GiB，随后在 `nn.Linear.__init__` 内部触发 access violation（可复现）。
用 `faulthandler` 才看到崩溃点：

```
Windows fatal exception: access violation
  File ".../torch/nn/modules/linear.py", line 109 in __init__
  File "vggt_omega/models/layers/ffn_layers.py", line 44 in __init__
```

**修复**：`scripts/torch_stream_loader.py` 按 zip 条目逐个读张量，峰值只占一个张量。
与 `torch.load` 数值一致（`allclose=True`），加载 4.3 GiB 用 **16 s**。

**补充排查（避免误归因）**：我一度以为这是"OpenMP 多线程"问题，但实测
`OMP_NUM_THREADS=1` 与 `=8` 都能正常构造模型，**线程数不是原因**。可复现的最小触发序列是：

```
[built]                 ← 构造模型，正常
[loaded] 1411           ← 流式载入 4.6 GiB 权重，正常
                        ← 此处再构造一个模型 -> access violation，进程直接死
```

而"构造 → 释放 → 再构造"不崩，说明是**已驻留 4.6 GiB 权重后进程地址空间的碎片/预留**问题，
不是线程栈。保留 `OMP_NUM_THREADS=1` 只是顺手降低峰值，**不能**当成已定位的根因。

### 8. WSL 上 `torch.load` 失败

同一 checkpoint 在 WSL 的 DrvFs（`/mnt/...`）上会因 mmap 报 `OSError`。流式读取同样绕过。

### 9. ExMesh 在 Windows 上无法编译

| 组件 | 问题 | 修复 |
|---|---|---|
| `simple-knn` | `FLT_MAX` 未定义（GCC 13 不再隐式包含） | 加 `#include <cfloat>` |
| `diff-plane-rasterization` | `uint32_t` / `uintptr_t` 未定义 | 加 `#include <cstdint>` |
| `nvdiffrast` | PyPI 无包 | 源码安装 0.4.0 |
| `train.py` | mask 按原图尺寸读，图像已缩放 → 624 vs 512 报错 | mask 缩放到渲染分辨率 |

Windows 侧无法编译（缺 Windows SDK，`cl.exe` 找不到 `stdio.h`），因此改在 WSL2（CUDA 12.8）构建。

### 10. ExMesh 纹理分辨率硬编码导致 OOM

`arguments/__init__.py` 写死 `texture_resolution = (2560, 2560)`，8 GiB 卡上烘焙顶点色到该尺寸会 OOM。
已改为读取环境变量 `EXMESH_TEX`（本次用 1024）。

### 11. 其他工程问题

- **xatlas 在 30 万顶点上耗时 293 s** 且长时间无输出；先简化到 12 万面（`fast-simplification`，1 s）再展开。
- **shell 脚本 CRLF** 导致 bash 报 `set: pipefail: invalid option name`；已统一 LF 并加 `.gitattributes`。
- **`pycolmap` 3.10 无 Python 3.12 Windows wheel**，且 4.x 改了 `Image.id` API；COLMAP 改为写**文本**格式（`cameras.txt` / `images.txt` / `points3D.txt`），不依赖 pycolmap。
- **单连接下载被限速**（ETH3D 0.05 MiB/s、NeRF 数据 14 KB/s）；`scripts/fetch_url.py` 8 连接分段下载，353 MB 用 **90 s**（235 MB/min）。

## 二、把"模型不准"和"后处理不行"分开

关键结论：**VGGT-Ω 的预测本身是准的，烂网格来自后处理。**

对照 ETH3D kicker 官方真值：

| 指标 | 数值 | 结论 |
|---|---|---|
| 相机中心误差（train-only Sim(3) 后） | **0.59%** 场景尺度（2.0 cm / 7.2 m） | ✅ 准 |
| 相机旋转误差 | **0.57°** 均值 / 1.21° 最大 | ✅ 准 |
| 内参焦距 | **−0.25%** vs 真值 | ✅ 准 |

最有说服力的一条：修好后处理后，**跨视图深度一致率从 0.168 → 0.819**，保留像素 16.2% → 92.0%。
如果 Ω 深度本身不准，调参数不可能让不同视角突然对齐。

注意：Ω 输出是**任意 gauge、非米制**（kicker 的 Sim(3) 缩放约 3.28），这是预期行为，不是错误。

## 三、仍未解决的问题（不要当成已解决）

### 3.1 背景/白底被融合成"外壳" ← **当前主要瓶颈**

**现象**：lego 的渲染里物体外面套着一层灰色板状壳，ExMesh 优化 700 步也去不掉
（它只调顶点和纹理，不会删除一整层错误几何）。

**量化**（lego 单帧）：

| 区域 | 图像亮度 | Ω 深度中位数 | Ω 置信度中位数 |
|---|---|---:|---:|
| 背景（占 82.5% 像素） | 0–60 | 0.840 | **3.7** |
| 物体 | >120 | 0.674 | **28.1** |

背景被预测出**合理深度**且置信度非零，所以会被 TSDF 当真。

**已做**：加绝对置信度阈值 `--conf-threshold 10`（lego 保留 34.7% 像素，网格从 222 万面降到 57 万面）。

**未做**：显式前景 mask。这是 ExMesh 官方做法，也是唯一能干净去掉外壳的手段。

### 3.2 网格不是闭合曲面

kicker 边界边 33,375、lego 36,277。这是"只观测到有限视角"的物理限制：背面本来就没拍到。
`MESH_UV_PIPELINE.md` 要求这类区域单独标记，不能当成重建结果。

### 3.3 迭代次数与纹理分辨率都不够

| | 本次 | ExMesh 官方 |
|---|---|---|
| 迭代 | 700 | 10,000 |
| 纹理 | 1024² | 2560² |
| 视图 | kicker 12/25、lego 16/100 | — |

**当前产物只能证明管线通，不能作为质量结论。**

### 3.4 没有跑官方几何评估

ETH3D 需要官方 scan 对齐 + 可见性协议才能报 Chamfer / F-score；DTU 同理。
**目前所有"几何好坏"的判断都基于可视检查和自洽性，不是 benchmark 数字。**

### 3.5 场景选择曾用错

`eth3d_kicker` 虽被文档称作"小场景"，实际是**拍摄运动器材库房**的大型室内场景，不是单物体。
适合物体级验证的数据是 NeRF-Synthetic `lego`（16 视角，800×800，真彩色）。

## 五、修复顺序建议

1. **前景 mask**（阻塞项）：`rembg` 或 SAM 生成 mask → 只融合 mask 内像素 → 重建 TSDF。
   判据：外壳消失、面数显著下降、网格变成单物体表面。
2. **ExMesh 跑满 10,000 步 + 2560² 纹理**（需要更多显存或分块）。
3. **几何评估**：接 ETH3D 官方 scan 对齐协议，报 Chamfer / F-score；否则无法与论文对比。
4. **多视角覆盖**：lego 用满 100 视角（当前 16），kicker 用满 25（当前受 8 GiB 限制）。

## 六、教训

这轮 11 个问题里，有 6 个是**"自洽但错"**：错误的 K 配上错误的深度、未观测区当成外部、
仿射重复缩放、材质默认值压暗贴图。单独看每个模块都"能跑"，只有**对着真值或打开文件**才暴露。

因此后续约束：

- 有真值时**必须**加断言（`sx·W ≈ model_width`、`K_original.f ≈ GT`、GLB 材质回读校验）；
- 没有真值时用**已知几何的合成场景**验证解析式；
- 文档里严格区分「已验证」与「计划中」，不把"跑通"写成"效果好"。
